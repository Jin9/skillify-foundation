# Acceptance Criteria

Mirrored from `.squad-run/ba.json`.

## Purpose

Design and build 7 backend services plus a Thai-language mobile customer web frontend that fulfill ShopPilot MVP's browse-cart-checkout-pay-track customer journey.

## Acceptance Criteria (44)

### AC-001

- **Given** An email not yet registered, a password meeting policy, and a name
- **When** The client POSTs to identity register
- **Then** The response is 200/201 with no password material in the body, a CUSTOMER account exists in the database, and the stored password is a one-way hash distinct from the plaintext (AUTH-001, AUTH-006)

### AC-002

- **Given** An email already registered
- **When** The client POSTs to identity register with that same email
- **Then** The response is a CONFLICT (409) with a code that signals duplicate email; no second user row is created (AUTH-001)

### AC-003

- **Given** A registered user with the correct password
- **When** The client POSTs to identity login
- **Then** Response contains an access token and a refresh token, the access token decodes to ES256 with shorter expiry than the refresh token, and both expiries are present (AUTH-002, AUTH-005)

### AC-004

- **Given** A wrong email OR a wrong password
- **When** The client POSTs to identity login
- **Then** Both cases return the same UNAUTHORIZED error code and the same human-readable message (AUTH-007)

### AC-005

- **Given** A valid CUSTOMER access token
- **When** The client calls an admin-only endpoint such as admin product create
- **Then** Response is FORBIDDEN (403) and no product is created (AUTH-003)

### AC-006

- **Given** A logged-in user with a refresh token
- **When** The client calls logout then attempts to use the same refresh token
- **Then** The second call is rejected with UNAUTHORIZED/INVALID_TOKEN and no new access token is issued (AUTH-004)

### AC-007

- **Given** An authenticated customer
- **When** The client GETs identity profile and then PATCHes name and phone
- **Then** GET returns name, email, phone, defaultAddress; PATCH succeeds for name and phone but a PATCH that mutates email returns VALIDATION_ERROR (CUST-001, CUST-002)

### AC-008

- **Given** An authenticated customer with no addresses
- **When** The client POSTs identity address-create with receiverName, phone, addressLine, province, district, postalCode, isDefault=true
- **Then** Response is 200/201, the address is persisted bound to the requesting userId, and the customer's defaultAddressId points to the new address (CUST-003, CUST-004)

### AC-009

- **Given** 1000 ACTIVE products seeded in catalog
- **When** Client GETs product listing with page=1 limit=20 sort=price_asc
- **Then** Response returns exactly 20 items sorted ascending by price, all ACTIVE and visible, and includes total count and page metadata (CAT-001, CAT-002)

### AC-010

- **Given** Products belonging to category C and others outside it
- **When** Client GETs product listing with categoryId=C and minPrice=100 and maxPrice=500 and inStock=true
- **Then** Every returned item belongs to category C, has price in [100,500], and has availableQty greater than zero (CAT-003, CAT-004, CAT-005)

### AC-011

- **Given** An ADMIN token and a category that exists
- **When** Admin POSTs product create with unique SKU, price > 0, that categoryId
- **Then** Product is created with status DRAFT or ACTIVE per request, the returned id is a UUID, and a duplicate-SKU retry returns CONFLICT (CAT-007, CAT-010)

### AC-012

- **Given** An ADMIN token and an existing product that appears in a historical order
- **When** Admin POSTs product soft-delete on that product
- **Then** Listing endpoints stop returning the product, but GETting the prior order's detail still resolves the product's snapshot fields (CAT-009)

### AC-013

- **Given** An ADMIN token and an existing category at the same level as another with the same proposed name
- **When** Admin POSTs category create
- **Then** Response is CONFLICT (409) and no category is created (CATE-001)

### AC-014

- **Given** A SKU with availableQty=10, reservedQty=0, soldQty=0
- **When** Checkout reserves 3 units and then payment-success is simulated
- **Then** After reservation availableQty=7 reservedQty=3 soldQty=0; after payment success availableQty=7 reservedQty=0 soldQty=3 (INV-002, INV-003, INV-005)

### AC-015

- **Given** A SKU with availableQty=7 reservedQty=3 soldQty=0 from an active reservation
- **When** Payment-failed is simulated for the owning order
- **Then** availableQty=10 reservedQty=0 soldQty=0 and the order moves to PAYMENT_FAILED (INV-006, PAY-003)

### AC-016

- **Given** An ADMIN token and a SKU
- **When** Admin POSTs stock-adjust with delta=-2 and reason='damaged'
- **Then** availableQty decreases by 2 and a stock-adjustment record exists with the delta, reason, and admin actorUserId (INV-007)

### AC-017

- **Given** An authenticated CUSTOMER and an ACTIVE product P
- **When** Customer POSTs cart add for P qty=2 twice in succession
- **Then** Cart contains a single line for P with quantity=4 and updatedAt advanced (CART-006, CART-007)

### AC-018

- **Given** An authenticated CUSTOMER with a cart line for product P qty=2 and P availableQty=1
- **When** Customer POSTs cart edit setting qty=3
- **Then** Response is a validation error referencing availableQty=1 and the cart line is unchanged (CART-002)

### AC-019

- **Given** An authenticated CUSTOMER with a cart line for product P
- **When** Customer POSTs cart remove on that line
- **Then** Response is 200, the cart no longer contains a line for P, and the cart subtotal is recalculated from the remaining lines (CART-003, CART-004)

### AC-020

- **Given** An authenticated CUSTOMER with a non-empty cart, a valid owned address, and an Idempotency-Key K1
- **When** Customer POSTs checkout twice with the same Idempotency-Key K1
- **Then** Exactly one order is created, both calls return that same order id, and stock is reserved exactly once (CHK-001, CHK-002, CHK-007, CHK-008, CHK-009)

### AC-021

- **Given** A cart with one line of qty=5 against a SKU with availableQty=2
- **When** Customer POSTs checkout
- **Then** Response is 409 INSUFFICIENT_STOCK with details listing that productId, requestedQty=5, availableQty=2, and no order is created (CHK-004)

### AC-022

- **Given** A valid checkout request whose body claims total=1 baht
- **When** Customer POSTs checkout
- **Then** The created order's total equals the server-computed sum of (current price * quantity) per item plus the §11.2 shipping fee, ignoring the client-supplied total (CHK-005)

### AC-023

- **Given** A cart whose only product transitioned to INACTIVE after add
- **When** Customer POSTs checkout
- **Then** Response rejects with a per-item error referencing that product, no order is created, and stock is not reserved (CHK-003, CART-005)

### AC-024

- **Given** A successful checkout that ordered the cart's only line
- **When** Customer GETs cart afterward
- **Then** Cart is empty (CHK-010)

### AC-025

- **Given** Customer A's order O_A and Customer B's access token
- **When** Customer B GETs orders listing or GETs order O_A by id
- **Then** Listing does not include O_A and direct GET returns NOT_FOUND or FORBIDDEN; never the order body (ORD-001)

### AC-026

- **Given** An order moved through PENDING_PAYMENT → PAID → PACKING
- **When** Customer GETs order detail
- **Then** Response includes item lines with priceSnapshot, addressSnapshot, currentStatus=PACKING, and status history with three rows in chronological order each carrying actor and timestamp (ORD-002, ORD-007, ORD-009)

### AC-027

- **Given** An order in DELIVERED state
- **When** Admin POSTs order cancel
- **Then** Response is 409 INVALID_ORDER_STATE and the order remains DELIVERED (ORD-003)

### AC-028

- **Given** An order in PENDING_PAYMENT belonging to the requesting customer
- **When** Customer POSTs order cancel
- **Then** Order moves to CANCELLED, reserved stock is released back to availableQty, and a status-history row is written (ORD-004)

### AC-029

- **Given** An order in PAID state and an ADMIN token
- **When** Admin POSTs order cancel with reason='out of stock'
- **Then** Order moves to CANCELLED, the reason is persisted on the cancellation record, and stock previously sold is released back to availableQty per MVP policy (ORD-005)

### AC-030

- **Given** An ADMIN token and an order whose current status is PACKING (or SHIPPED, or DELIVERED)
- **When** Admin POSTs order cancel with a reason
- **Then** admin-cancel from PENDING_PAYMENT or PAID succeeds and emits order.cancelled; admin-cancel from PACKING or later returns 409 INVALID_ORDER_STATE and the order is unchanged (ORD-005, §9.2, §9.3)

### AC-031

- **Given** An order in PACKING and an ADMIN token
- **When** Admin POSTs order ship without a tracking number
- **Then** Response is VALIDATION_ERROR and the order remains PACKING (ORD-006)

### AC-032

- **Given** A successful checkout that produced order O with total T
- **When** Server-side payment intent creation runs
- **Then** Payment intent exists with status REQUIRES_PAYMENT, amount=T, and is linked to O (PAY-001)

### AC-033

- **Given** A payment intent in REQUIRES_PAYMENT for order O
- **When** The same payment-success callback is delivered twice
- **Then** Order O ends in PAID exactly once, soldQty increased exactly once, and the second callback returns 200 with no additional state change (PAY-002, PAY-005)

### AC-034

- **Given** A payment intent for order O with amount T
- **When** A payment-success callback arrives with amount != T
- **Then** Response is 409 PAYMENT_AMOUNT_MISMATCH, order O remains PENDING_PAYMENT, stock reservation unchanged (PAY-006)

### AC-035

- **Given** Any payment intent that resolves
- **When** It transitions to a terminal status
- **Then** The persisted payment row contains mockPaymentRef, providerStatus, and paidAt (PAY-007)

### AC-036

- **Given** Customer has a cart with subtotal of 1499 THB
- **When** checkout.preview is called
- **Then** The response sets shippingFee=60 and grandTotal=1559 (§11.2)

### AC-037

- **Given** Customer has a cart with subtotal of 1500 THB
- **When** checkout.preview is called
- **Then** The response sets shippingFee=0 and grandTotal=1500 (§11.2 threshold; subtotal ≥ 1500 ⇒ free shipping)

### AC-038

- **Given** An unauthenticated visitor opens the customer mobile webview
- **When** The home tab route renders
- **Then** The page declares lang='th', the layout fits a 390-wide viewport with a single column, the bottom tab bar shows the 5 tabs (home/search/cart/orders/profile), the primary CTA colour matches the emerald brand token, prices render with the ฿ Thai-Baht prefix, and product cards open the detail route on tap (Frontend Spec §1, §2, §3)

### AC-039

- **Given** An unauthenticated visitor on the cart, orders, profile, checkout, payment, orderDetail, or addresses route
- **When** The route is opened without a stored access token
- **Then** The app redirects to the login route and, after successful login, returns the customer to the route they originally requested (Frontend Spec §3 'Auth?' column)

### AC-040

- **Given** An authenticated customer with at least one cart line and one default address
- **When** The customer drives the mobile webview through home → search → detail → add-to-cart → cart → checkout → payment-success → orderSuccess → orderDetail
- **Then** The end-to-end journey completes without error, the orderDetail route shows status=PAID, item snapshots, address snapshot, and a status-history with at least PENDING_PAYMENT and PAID entries (Frontend Spec §3 + ORD-002, ORD-009)

### AC-041

- **Given** An authenticated customer whose cart subtotal is 1500 THB on the checkout route
- **When** The checkout route renders the totals block
- **Then** shippingFee shows ฿0 and grandTotal shows ฿1,500; reducing the cart so subtotal is 1499 re-renders shippingFee as ฿60 and grandTotal as ฿1,559 (Frontend Spec §5 + §11.2)

### AC-042

- **Given** An authenticated customer on the payment route after a successful checkout
- **When** The customer taps simulate-success, simulate-failed, or simulate-timeout
- **Then** The app calls the payment service for the chosen outcome, then routes to orderSuccess on PAID, or to orderResult on PAYMENT_FAILED / PAYMENT_EXPIRED, surfacing the order number and a deep link into orderDetail (Frontend Spec §5, PAY-002, PAY-003, PAY-004)

### AC-043

- **Given** An authenticated customer with three orders in different statuses
- **When** The customer opens the orders tab and toggles the all / active / done filter
- **Then** The list renders one row per order with a coloured status badge carrying a Thai label and tapping a row opens orderDetail for that order (Frontend Spec §3 + ORD-001)

### AC-044

- **Given** Any successful or failed API call from the frontend or a backend caller
- **When** The client inspects the response body
- **Then** The body conforms to the envelope { code, message, data, traceId } where traceId is a non-empty string and code is a documented error code on failure (cross-cutting)

## Edge cases (17)

- {"case": "Stock for a SKU drops below the cart quantity between add-to-cart and checkout", "expected": "Checkout returns 409 INSUFFICIENT_STOCK with per-item availableQty and requestedQty; no order is created; no stock is reserved (CHK-004, INV-008)"}
- {"case": "Customer simulates payment timeout on a PENDING_PAYMENT order", "expected": "Order moves to PAYMENT_EXPIRED, reservedQty is released back to availableQty, and a status-history row is written (PAY-004, INV-006)"}
- {"case": "Payment provider redelivers the same success callback for the same paymentIntentId", "expected": "Second delivery is recognized via idempotency on (paymentIntentId, providerStatus); order state and stock are unchanged from the first delivery (PAY-005)"}
- {"case": "Two concurrent checkouts try to reserve the last unit of the same SKU", "expected": "Exactly one checkout succeeds and creates an order with reservation; the other receives 409 INSUFFICIENT_STOCK; availableQty never goes negative (INV-008, CHK-004)"}
- {"case": "Customer views order history that includes a product later soft-deleted by admin", "expected": "Order detail still resolves the product's name, image, and priceSnapshot from the order item snapshot rather than from the live catalog (CAT-009, ORD-007)"}
- {"case": "Client replays a checkout with a previously used Idempotency-Key but with a different cart payload", "expected": "Server returns the originally created order for that key without creating a new order, and does not silently honor the new payload (CHK-009)"}
- {"case": "Product price is changed by admin after an item was added to cart but before checkout submit", "expected": "Server-side checkout uses the price at the moment of order creation (or pre-declared snapshot per design) and writes that price into the order item snapshot; client-supplied total is ignored (CHK-005, ORD-007)"}
- {"case": "Customer submits checkout referencing a shipping address belonging to a different customer", "expected": "Checkout returns FORBIDDEN/VALIDATION_ERROR and no order is created (CHK-002)"}
- {"case": "Customer calls an authenticated endpoint with an expired access token", "expected": "Response is 401 UNAUTHORIZED with the documented code; no business state is mutated (AUTH-005)"}
- {"case": "Admin tries to transition order from SHIPPED back to PAID", "expected": "Response is 409 INVALID_ORDER_STATE; order stays SHIPPED (ORD-003, section 9.3)"}
- {"case": "Customer tries to cancel an order that has already moved to PAID", "expected": "Customer-cancel returns 409 INVALID_ORDER_STATE; only ADMIN can cancel a PAID order with a reason (ORD-004, ORD-005)"}
- {"case": "Cart contains an item whose product became INACTIVE before checkout", "expected": "Cart UI marks it non-checkoutable and checkout rejects until the customer removes it (CART-005, CHK-003)"}
- {"case": "Customer hits checkout.commit but never simulates payment (browser closed / user walks away)", "expected": "Within the reservation TTL, the order moves PENDING_PAYMENT → PAYMENT_EXPIRED, the reserved stock is released back to availableQty, and a status_history row records the transition (INV-004, PAY-004, ORD-009)"}
- {"case": "Cart subtotal lands exactly on the §11.2 threshold (subtotal = 1500 THB)", "expected": "Server applies shippingFee=0 (the ≥ 1500 branch); subtotal=1499 instead applies shippingFee=60. Boundary is inclusive at 1500 (§11.2)"}
- {"case": "Unauthenticated visitor opens the cart, orders, profile, checkout, payment, orderDetail, or addresses route via deep link", "expected": "Frontend redirects to the login route and after successful login resumes the originally requested route (Frontend Spec §3 'Auth?' column)"}
- {"case": "Frontend payment route is closed by the customer before any simulate button is tapped", "expected": "The order remains PENDING_PAYMENT until the reservation TTL elapses and then transitions to PAYMENT_EXPIRED with stock released; the orders tab still surfaces the order with the resulting status (PAY-004, INV-004)"}
- {"case": "Frontend runs on a viewport narrower than 390 (e.g. 360-wide Android Chrome)", "expected": "The single-column layout reflows without horizontal scroll, the bottom tab bar remains anchored, and the primary CTAs remain tappable (Frontend Spec §1)"}
